# 进度查询与工程审查

本文与 [无限画布开发方案](无限画布开发方案.md) 并列，是本项目的两份主文件之一。

- **开发方案**写边界、字段、接口、阶段范围和验收句子。实现以那一份为准。
- **本文**写现在做到哪一步、预定功能完成了没有、某一阶段能不能进入审查、审查过了没有。进度只写在这里，不要改写方案正文来记进度。

任何对话、规划、实现、审查开始之前，必须先读这两份主文件。读完之前不要改产品代码，也不要另开一套阶段划分。

过程稿在 `docs/plan-notes/`，不是主文件。`eval/` 不是本产品模块。

## 1. 怎么用这份文件

### 1.1 阶段状态

| 状态 | 含义 | 谁改 |
| --- | --- | --- |
| 未开始 | 范围里的实现还没动手 | 进入该阶段第一天改为「进行中」 |
| 进行中 | 正在做，还不能交审查 | 开发者 |
| 待审查 | 范围、演示脚本、生效预算都做完并填了记录表，等人审 | 开发者在自检通过后改 |
| 审查失败 | 审过，有必须改的问题 | 审查者。改完后由开发者重新标「待审查」 |
| 已通过 | 审查成功，这一阶段关闭 | 审查者。同时更新第 2 节快照和第 4 节功能表 |
| 后置 | 本版本明确不做 | 方案已定为后置的阶段，不要改成已通过来「跳过」 |
| 可后移 | 不做也不挡前面的阶段 | 阶段 8。若决定砍掉，在快照里写「本版本不做」，不要假装已通过 |

只有「已通过」能把「当前阶段」指针往后推。开发者不能自己把「进行中」改成「已通过」。

阶段 10 人周为 0，状态保持「后置」，直到有人明确开工壳。阶段 1–9 的通过不依赖壳。

### 1.2 功能状态

| 状态 | 含义 |
| --- | --- |
| 未开始 | 还没做 |
| 进行中 | 所属阶段已开工，这项还没达到方案里的验收 |
| 待审查 | 功能本身能演示，但所属阶段还没审查通过 |
| 已验收 | 所属阶段已通过，这项按方案兑现 |
| 不做（第一版） | 方案第 3 节或该阶段「非范围」写明不做 |
| 可后移 | 阶段 8 一类；砍掉不影响 1–7 |

一项功能标「已验收」，必须等到**绑定阶段**审查通过。阶段 3 做出来的按钮，要到阶段 5 才真正跑全的，在表里分成两行，不要提前勾完。

### 1.3 审查流程

```text
当前阶段范围内的实现做完
        │
        ▼
按开发方案该阶段「演示脚本」走一遍
按第 12.4 节记录表填写：通过 / 不通过 / 未观察
生效预算行至少观察一次；未观察 ≠ 通过
视觉最低线看过；禁用按钮有原因句
        │
        ▼
把该阶段改为「待审查」，填「提交审查」栏
        │
        ▼
审查者对照本文第 6 节清单 + 方案该阶段全文
        │
   ┌────┴────┐
   ▼         ▼
已通过     审查失败
更新快照    列出问题，停在本阶段
功能表      开发者改完后重新「待审查」
指针后移    不得跳阶段
```

审查失败时继续改**当前阶段**的问题。不要用「先做下一阶段再补」来关闭失败项，除非失败项本身属于方案写明的可后移范围。

### 1.4 更新规则

改这份文件时只改状态、日期、记录、审查结论和功能表勾选。不要在这里改产品字段、接口或验收句子；那些有变，先改开发方案，再回头改本文对应清单。

每次审查通过或失败，都要在第 7 节追加一条记录。不要删旧记录。

## 5. 提交审查时必填

开发者把阶段改为「待审查」时，在该阶段小节的「提交审查」表里填写。空表不能审。

演示记录按方案第 12.4 节抄列。结论只允许：通过 / 不通过 / 未观察。未观察不得当成通过。

通用门槛（每一阶段都要满足，才允许待审查）：

1. 方案该阶段「范围」里的模块和接口都有着落；「非范围」没有偷偷做完并当成通过。
2. 该阶段每一条演示脚本都有记录。
